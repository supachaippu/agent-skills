# Proteus: Safe Code Modification & Regression-Free Refactoring

เมื่อต้องแก้ไขโค้ดเดิม, ปรับปรุงฟังก์ชันที่มีอยู่, ปรับโครงสร้างระบบ (Refactor), หรือพิมพ์ `/proteus`, "แก้โค้ดเดิม", "ปรับโครงสร้าง", "modify code":
ให้ปฏิบัติตามขั้นตอนและ **จุดเบรกบังคับหยุด (Hard Blocking Gates)** เพื่อป้องกันความเสี่ยง 100%:

---

## กฎเหล็กสูงสุด: มาตรการล็อกขอบเขตการแก้ไขโค้ด (Strict Code Preservation)
- **ห้ามลบโค้ดเดิมโดยพลการ:** ห้ามลบ ปรับโครงสร้าง หรือทำความสะอาดโค้ด (Cleanup) ส่วนที่ทำงานถูกต้องอยู่แล้ว หากไม่ได้ถูกสั่งการให้แก้ไขโดยตรง
- **ห้ามตัด Feature เดิม:** โค้ดที่ทำงานได้อยู่แล้วต้องคงความสามารถเดิมไว้ครบถ้วน 100%
- **คงคอมเมนต์เดิม:** รักษารูปแบบคอมเมนต์เดิมและการทำงานเดิมไว้ทั้งหมด

---

## ขั้นตอนที่ 1: ตรวจสอบและประเมินผลกระทบ (Code Review & Blast Radius)
- **ประสานงานสกิล:** `code-review`
- ศึกษาสถานะปัจจุบันของโค้ดที่จะแก้ไข ทำความเข้าใจ Call stack และ Data flow
- ระบุจุดเชื่อมโยง (Dependencies) และประเมินผลกระทบต่อโมดูลอื่น (Blast radius)

---

## ขั้นตอนที่ 2: จุดเบรกที่ 1 — แสดงแผนการแก้ไขและรอรับอนุมัติ (MANDATORY REFACTOR PLAN)
- 🛑 **คำสั่งเบรกแตก (CRITICAL HARD STOP):**
  - **ห้ามลงมือแก้โค้ดหรือเขียนทับไฟล์ใดๆ ในรอบแรกเด็ดขาด**
  - AI ต้องสรุป **แผนการแก้ไข (Implementation Plan)** ให้ผู้ใช้ตรวจสอบก่อน:
    1. **รายชื่อไฟล์ที่จะแก้ไข (Affected Files):** ระบุชื่อไฟล์และฟังก์ชันที่ต้องแตะต้องอย่างชัดเจน
    2. **เหตุผลและความจำเป็น:** อธิบายว่าทำไมต้องแก้ส่วนนี้ และแก้เพื่ออะไร
    3. **การยืนยันความปลอดภัย:** ยืนยันว่าไม่มีการลบฟีเจอร์เดิม และฟังก์ชันข้างเคียงจะไม่ได้รับผลกระทบ
  - **หยุดรอคำยืนยันอนุมัติจากผู้ใช้ก่อน จึงจะเริ่มลงมือแก้ไขจริงได้**

---

## ขั้นตอนที่ 3: ล็อกพฤติกรรมเดิมด้วยแบบทดสอบ (Lock Behavior via TDD)
- **ประสานงานสกิล:** `tdd`
- ก่อนลงมือแก้โค้ด ให้เขียนหรือรัน Test เพื่อยืนยันว่าพฤติกรรมเดิมที่ถูกต้องยังคงทำงานได้ (Regression safety net)
- ยืนยันว่าชุดทดสอบเดิมรันผ่านทั้งหมด

---

## ขั้นตอนที่ 4: ลงมือแก้ไขอย่างแม่นยำและจำกัดขอบเขต (Surgical Implementation)
- **ประสานงานสกิล:** `implement`
- ทำการแก้ไขเฉพาะจุดที่ได้รับอนุมัติ โดยแก้ไขให้น้อยที่สุดและตรงจุดที่สุด (Surgical patch)

---

## ขั้นตอนที่ 5: เสริมความลึกของสถาปัตยกรรม (Improve Architecture)
- **ประสานงานสกิล:** `improve-codebase-architecture`
- หากเป็นการ Refactor ให้ยึดหลัก Deep Modules:
  - ลดความซับซ้อนของ Public API
  - กักเก็บตรรกะภายในไว้ให้เป็นระเบียบ ไม่เปิดเผย Internal state ออกมาเกินจำเป็น

---

## ขั้นตอนที่ 6: ตรวจสอบอิสระรอบด้านป้องกันผลข้างเคียง (External Scrutiny)
- **ประสานงานสกิล:** `scrutinize`
- จำลองมุมมองจากผู้ตรวจสอบภายนอก (Outsider perspective):
  - โค้ดที่แก้ทำงานตรงตามคำสั่งจริงหรือไม่?
  - มี Side effects หรือพฤติกรรมแฝงที่ไม่พึงประสงค์หรือไม่?
- รันชุดทดสอบทั้งหมดอีกครั้งเพื่อยืนยันความสมบูรณ์ 100%
