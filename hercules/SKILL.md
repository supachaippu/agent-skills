# Hercules: Systematic Bug Hunting, Diagnosis & Remediation Pipeline

เมื่อระบบเกิดข้อผิดพลาด, มีบัค, โปรแกรมพัง, หรือผู้ใช้พิมพ์ `/hercules`, "แก้บัค", "debug", "หาบัค", "error":
ให้ปฏิบัติตามวินัยการแก้บัคแบบเป็นระบบ พร้อม **จุดเบรกบังคับหยุด (Hard Blocking Gates)** ห้ามเดาสาเหตุหรือแก้โค้ดสุ่มสี่สุ่มห้าเด็ดขาด:

---

## ขั้นตอนที่ 1: ท่องบทสวดดีบัก 4 ข้อออกมาทันที (Recite Debug Mantra Verbatim)
- **ประสานงานสกิล:** `debug-mantra`
- 🛑 **กฎบังคับ:** ในบรรทัดแรกสุดของคำตอบแรก AI **ต้องแสดงกล่องข้อความบทสวดนี้ verbatim เสมอ**:

> **Debug Mantra:**
> 1. **First is reproducibility.** ต้องจำลองบัคให้เกิดขึ้นซ้ำได้แน่นอน 100% ก่อนทำสิ่งอื่น
> 2. **Know the fail path.** แกะรอยเส้นทางล้มเหลวจากจุดพังย้อนกลับไปหาต้นทาง
> 3. **Question your hypothesis.** ตั้งสมมติฐานแล้วทดสอบเพื่อหักล้าง อย่าปักใจเชื่อข้อแรก
> 4. **Every run is a breadcrumb.** บันทึกและเชื่อมโยงหลักฐานการทดสอบทุกครั้ง

---

## ขั้นตอนที่ 2: จุดเบรกที่ 1 — ยืนยันการจำลองบัค (MANDATORY REPRO CHECK)
- สร้างคำสั่งทดสอบเพื่อจำลองบัคให้เกิดขึ้นซ้ำ (เช่น รันสคริปต์, curl, หรือเรียกคำสั่งที่พัง)
- 🛑 **คำสั่งเบรกแตก (CRITICAL STOP IF NO REPRO):**
  - หาก **ไม่สามารถจำลองบัคได้ (No reproduction / Flaky):**
  - **AI ต้องหยุดทันที ห้ามลงมือแก้ไขโค้ดเด็ดขาด!**
  - ให้แจ้งผู้ใช้พร้อมระบุสิ่งที่ต้องการเพิ่มเติม (เช่น ข้อมูล Log เพิ่มเติม, ตัวแปร Input ที่ทำให้เกิดปัญหา, หรือภาพหน้าจอ)

---

## ขั้นตอนที่ 3: วินิจฉัยหาสาเหตุที่แท้จริง (Deep Diagnosis Loop)
- **ประสานงานสกิล:** `diagnosing-bugs`
- บันทึกพฤติกรรมจริง (Actual) เทียบกับพฤติกรรมที่ควรจะเป็น (Expected)
- ค้นหาจุดแตกหักที่แน่นอนในโค้ด (Root Cause) **โดยยังไม่แก้ไขโค้ดใดๆ ทั้งสิ้นในขั้นตอนนี้**

---

## ขั้นตอนที่ 4: จุดเบรกที่ 2 — ล็อกบัคด้วยแบบทดสอบที่ล้มเหลว (Pin Bug via Failing Test)
- **ประสานงานสกิล:** `tdd`
- เขียน Unit Test หรือ Integration Test ที่จำลองเงื่อนไขที่ทำให้เกิดบัค
- รันแบบทดสอบและ **ต้องแสดงผลลัพธ์สถานะ RED (Fail) ให้เห็นชัดเจน** เพื่อพิสูจน์ว่าแบบทดสอบจับจุดผิดพลาดได้จริง

---

## ขั้นตอนที่ 5: ผ่าตัดแก้ไขเฉพาะจุดอย่างแม่นยำ (Surgical Fix)
- ดำเนินการแก้ไขโค้ดที่เป็นต้นตอของบัคโดยใช้การแก้ไขที่เล็กและปลอดภัยที่สุด (Minimal surgical fix)
- **กฎเหล็ก:** ปฏิบัติตามมาตรการ Strict Code Preservation ห้ามลบ ปรับแต่ง หรือแตะต้องฟังก์ชันข้างเคียงที่ทำงานถูกต้องอยู่แล้วเด็ดขาด

---

## ขั้นตอนที่ 6: ยืนยันผลการแก้ไข (Verify Green)
- รันแบบทดสอบที่เขียนไว้ในขั้นตอนที่ 4 จนได้สถานะ **GREEN (Pass)**
- รัน Regression test ทั้งหมดเพื่อยืนยันว่าไม่มีสิ่งใดพังต่อเนื่อง

---

## ขั้นตอนที่ 7: จัดทำบันทึกวิเคราะห์สาเหตุเชิงวิศวกรรม (Post-Mortem / RCA)
- **ประสานงานสกิล:** `post-mortem`
- สรุปรายงาน Root Cause Analysis (RCA) สั้นๆ:
  - สาเหตุที่แท้จริง (Root Cause)
  - กลไกที่ทำให้เกิดความผิดพลาด (Failure Mechanism)
  - วิธีการแก้ไขและผลการตรวจสอบ (Fix & Validation)
  - แนวทางป้องกันไม่ให้เกิดซ้ำในอนาคต (`retro`)
