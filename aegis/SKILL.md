# Aegis: Universal Safety Shield & System Guardrails

เมื่อได้รับการเรียกใช้ผ่านคำสั่ง `/aegis`, เมื่อเริ่มต้นโปรเจกต์ใหม่, หรือเมื่อสลับเข้าสู่โฟลเดอร์งานใดๆ ให้ AI ยึดถือและปฏิบัติตามกฎเหล็กความปลอดภัยทั้ง 6 ข้อต่อไปนี้อย่างเคร่งครัดสูงสุด:

---

## 1. ฐานข้อมูล SAP SQL Server: โหมดอ่านอย่างเดียว 100% (Strict SAP Read-Only)
ในการทำงานกับฐานข้อมูล SAP SQL Server หรือ API ที่เกี่ยวข้องกับระบบ SAP:
- **อนุญาตเฉพาะคำสั่งดึงข้อมูลเท่านั้น:** ให้ใช้เฉพาะคำสั่ง `SELECT` หรือการ Query เพื่อการอ่านและสืบค้นข้อมูลเท่านั้น
- **ห้ามแก้ไข เขียน หรือลบข้อมูลเด็ดขาด:** ห้ามรันคำสั่ง SQL ที่เป็นการเปลี่ยนแปลงโครงสร้างหรือข้อมูลใดๆ (เช่น `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`, `TRUNCATE`, `MERGE` หรือ DDL/DML อื่นๆ) เป็นอันขาด
- **ข้อยกเว้นกรณีพิเศษ:** การอัปเดตฟิลด์ `EnbApprDI` ในตาราง `OADM` เป็น `'Y'` จะกระทำได้ต่อเมื่อได้รับคำสั่งและการยืนยันโดยตรงจาก "ป๋า" ในแชทนี้อย่างชัดเจนเท่านั้น

---

## 2. การล็อกขอบเขตโฟลเดอร์ (Strict Folder Boundary Containment)
- **จำกัดพื้นที่การทำงาน (Strict Scope):** ระบุโฟลเดอร์ของโครงการปัจจุบันที่กำลังทำอยู่ และจำกัดการอ่าน, การเขียน, การแก้ไข, และการสร้างไฟล์ทั้งหมดให้อยู่ภายในขอบเขตโฟลเดอร์นั้นเท่านั้น
- **ห้ามยุ่งกับโฟลเดอร์อื่นโดยไม่ได้รับอนุญาต:** ห้ามข้ามไปอ่าน แก้ไข หรือแตะต้องไฟล์ในโฟลเดอร์อื่น หรือโฟลเดอร์พี่น้อง (Sibling directories) โดยไม่ได้รับคำสั่งอนุมัติจากผู้ใช้อย่างชัดเจน
- **ห้ามรันคำสั่งใน Root Workspace:** **CRITICAL: ห้ามรันคำสั่ง Git, npm, pip หรือสคริปต์ใดๆ ใน Root `/Users/bart/ไฟล์ดิบ` เด็ดขาด** ต้องทำงานอยู่ภายในโฟลเดอร์ของโปรเจกต์ย่อยนั้นๆ เสมอ

---

## 3. การสงวนรักษาโค้ดเดิมอย่างเคร่งครัด (Strict Code Preservation)
- **ห้ามลบโค้ดเดิมโดยพลการ:** ห้ามลบ ปรับโครงสร้าง (Refactor) หรือทำความสะอาดโค้ด (Cleanup) ที่ส่งผลให้ฟีเจอร์เดิมสูญหายหรือถูกจำกัดความสามารถ หากโค้ดส่วนนั้นทำงานถูกต้องอยู่แล้ว ให้คงไว้ในสภาพเดิมทุกประการ
- **ห้ามลบโค้ดใดๆ ที่ไม่ได้บอกให้แก้ไข:** คงโค้ดเดิม, คอมเมนต์, และรูปแบบการทำงานเดิมไว้ทั้งหมด
- **การแจ้งเตือนล่วงหน้า:** หากจำเป็นต้องแก้ไขโค้ดเกี่ยวโยงในส่วนอื่น ต้องแจ้งข้อจำกัด แสดงแผนงาน (Implementation Plan) และรอรับคำยืนยันอนุมัติจากผู้ใช้ก่อนลงมือแก้ไขจริงเสมอ

---

## 4. ระบบป้องกันการจัดการเอกสาร PR ใน SAP (Direct PR Guardrail)
- ทุกครั้งที่มีคำสั่งให้สร้าง (Add), ลบ (Delete) หรือปิดสถานะ (Close/Cancel) ใบขอซื้อ (PR) ผ่านทางแชท **AI ต้องทำการทวนคำถามเพื่อขอความยืนยันจากผู้ใช้ก่อนเสมอ**
- ห้ามลงมือรันสคริปต์หรือยิงคำสั่งจัดการเอกสาร PR ก่อนได้รับคำตอบยืนยันที่ชัดเจน (เช่น "ยืนยัน", "ทำเลย", "yes") เด็ดขาด

---

## 5. ห้ามการเขียนทับฐานข้อมูล Cloud D1 (Remote Seeding Prohibition)
- **ห้ามรันคำสั่งนำเข้าไฟล์ SQL เพื่อเขียนทับฐานข้อมูลบน Cloud D1 เด็ดขาด:** เช่น `npx wrangler d1 execute ... --file=seed.sql` เพื่อป้องกันความเสี่ยงในการล้างตารางฐานข้อมูลเดิม (Database Cleansing) ซึ่งจะทำให้ข้อมูลจริงสูญหาย

---

## 6. การตรวจสอบบัญชี Cloudflare ก่อน Deploy (Cloudflare Account Guardrail)
- ก่อนทำการ Deploy หรือจัดการบริการบน Cloudflare ต้องรัน `npx wrangler whoami` ตรวจสอบบัญชีก่อนเสมอ:
  - โปรเจกต์ `ocrscreenitem` (Pages, D1: `ocrscreenitem-db`, R2: `ocrscreenitem-images`): ต้องล็อกอินบัญชี **`supachai.ppu@gmail.com`** เท่านั้น
  - โครงการและ Worker อื่นๆ ทั้งหมด: ต้องล็อกอินบัญชี **`ocrsparepart@gmail.com`** เท่านั้น

---

## 7. นโยบายฐานข้อมูลและระบบแคช (Database, Storage & Cached Egress)
- **ยึด Supabase เป็นศูนย์กลางข้อมูลและแคชหลัก:** อะไรที่เกี่ยวข้องกับ Database, Data Storage, หรือการเก็บสถานะของระบบ ให้ใช้ **Supabase (PostgreSQL)** เป็นหลัก
- **การใช้งาน Cached & Storage:** เนื่องจาก Supabase มีระบบ **Cached Egress** และ **Storage** สำหรับการแคชและเสิร์ฟข้อมูลในตัวอยู่แล้วที่มีประสิทธิภาพและตรวจสอบปริมาณการใช้งานได้ชัดเจน ให้ใช้ฟีเจอร์นี้ของ Supabase ในการจัดการแคชข้อมูล
- **หลีกเลี่ยงการพึ่งพา Cloudflare KV:** หลีกเลี่ยงการนำ Cloudflare KV มาใช้เป็น Database หรือที่เก็บแคชหลักของระบบ เนื่องจากขีดจำกัดความจุ โควตาการอ่าน/เขียน และพฤติกรรมการแคชของ Cloudflare KV ยังมีความไม่แน่นอนและตรวจสอบขีดจำกัดได้ยาก การรวมศูนย์ข้อมูลและแคชไว้ที่ Supabase จะทำให้ระบบมีความเสถียร ตรวจสอบง่าย และลดความซับซ้อนของสถาปัตยกรรม
